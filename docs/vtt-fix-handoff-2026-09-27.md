## 1. Sync and transport

### 1.1 Map-design events are far too large for Pusher (HIGH)

**Problem.** `environment.set` (see `SyncV2Store.php`, the board-domain branch that
calls `SceneEnvironment::apply`) emits `environment.changed` whose payload is the
*entire* `sceneConfig.environment`, that is every field together:

- terrain: an `n × m` grid of height samples, 4 per square in each direction, up to
  201×201 ≈ 40,000 numbers;
- walls: every node and segment plus roofs and ramps (Elfsong has 1,133 segments);
- exploration.

Opening one door re-sends all of it. Pusher Channels messages are limited to about
10 KB, and `SyncV2PusherTransport::publish` / `publishAudiences` only `error_log` a
failure. Players then see the change only when a later event reveals a revision gap
and triggers recovery. Every such event is also stored whole in the events table.
The reliability pass ran with Pusher blocked, so none of this was ever exercised
over real Pusher.

**Fix.**

1. **Door and window toggles get their own small command.** For example
   `environment.portal.set` with payload `{segmentId, open}`:
   - GM-only;
   - reject if the segment is not a door or window, or if it is locked;
   - apply to `environment.walls`, bumping the walls revision;
   - emit a small event such as `{segmentId, open, wallsRevision}`.

   The client applies it as a patch to its walls model, and also rebuilds the wall
   model the vision code uses. Portal buttons in `wall-editor.mjs` (`portals()`)
   must call this command instead of saving the whole walls document.
2. **Only send the changed field.** An `environment.set` for `walls` emits only the
   walls field; for `terrain`, only terrain.
3. **Terrain edits send only the changed region.** Add a patch form: the affected
   index rectangle `{i0, j0, i1, j1, values[]}` plus `expectedRevision`. A brush
   stroke tracks the min/max vertex indices it touched. The server validates the
   patch and merges it into the stored grid.
4. **Large payloads become a notice plus a download.** When the projected event JSON
   would exceed a safe size (about 8 KB), publish only `{sceneId, field, revision}`.
   Clients that see a newer revision fetch the field through an authenticated GET
   (a new endpoint or the recovery endpoint), projected for players (see 1.5).
   Whole-map installs and imports of AI-generated maps go this way.
5. Update the client reducer (`sync-v2/event-reducer.js`, `environment.changed`) and
   `environment-sync.mjs` for patch, portal and notice events. Keep recovery
   snapshots complete.
6. Tests:
   - event-size assertions (a door toggle event is under 1 KB; no event carries both
     fields);
   - player projection of the new events;
   - a gap-then-recovery fetch.
7. Browser pass with real Pusher delivery enabled, if possible. Otherwise state
   clearly that it is unverified.

### 1.2 Undo for terrain and walls is wiped by the GM's own save (MEDIUM)

**Problem.** After a stroke or wall edit is saved, the server echoes the new revision
to everyone, including the GM. The GM's client cannot tell its own echo from a
foreign change, so it clears undo:

- `dnd/vtt/assets/js/ui/terrain-prototype.js`, around line 112: `undo=[]` when
  `shared.revision !== sharedTerrainRevision`;
- `dnd/vtt/assets/js/ui/wall-prototype.js`, `tick()`: `history=[]` on any shared
  revision change.

Only old localStorage-era scripts ever tested undo.

**Fix.**

- Record the revision the server returned for this client's own save. The ack from
  `submitEnvironmentCommand` includes the new `environment[field].revision`.
- When the incoming revision equals the one just acknowledged, adopt it silently and
  keep the history. Clear history only for a foreign revision.
- Keep the terrain Undo button's `disabled` state in sync with the undo array.
- Make undo itself a normal save (it already is). With 1.1, it is a patch for
  terrain.
- Test: stroke → ack → undo restores the previous field; a foreign change clears
  history.

### 1.3 Edits made while a save is in flight are silently discarded (MEDIUM)

**Problem.** `wall-prototype.js` `change(before)`:
`if(savingShared){model=before;render();return;}`. Any wall edit made during the
save round-trip is reverted with no message. Rapid wall-point clicks drop points,
and a second quick door click does nothing. Terrain similarly refuses to start a
stroke while saving (`pointerdown` returns when `savingTerrain`).

**Fix.**

- Keep the edit locally and set a `dirtyWhileSaving` flag.
- When the in-flight save resolves, immediately send the latest model with the new
  expected revision, coalescing any number of edits into one save.
- Allow terrain strokes during a save and queue them the same way.
- Door clicks no longer go through this path once 1.1 exists.
- If a queued save is rejected, show the existing "not confirmed" message; don't
  drop the edit silently.

### 1.4 Client and server disagree on valid wall data, and the wall loop can die (LOW–MED)

**Problem.**

- `SceneEnvironment::validate` accepts things the client's `validateWalls`
  (`wall-geometry.mjs`) rejects. Example: two segments joining the same node pair,
  which the client rejects via its `pairs` set.
- The wall `tick()` in `wall-prototype.js` calls `validateWalls(shared.value)` with
  no try/catch. A server-accepted document the client rejects throws, and
  `requestAnimationFrame` is never rescheduled. Walls, doors and vision then freeze
  for that client until reload.

**Fix.**

- Make the server reject everything the client rejects: duplicate node pairs, plus
  whatever `validateProperties` checks. Add the matching cases to
  `scene-environment.test.php`.
- Wrap the wall tick body in try/catch and always reschedule.
- On an invalid shared document, keep the last good model, disable editing, and
  show the GM a warning.

### 1.5 Secret doors must be invisible to players (MEDIUM)

**Problem.** Players receive the full walls document, including `secret:true` doors,
in snapshots, recovery and events. It is readable in browser dev tools.

**Required behaviour.**

- **GM:** secret doors show a **"?"** icon instead of the normal door icon in the
  portal controls (`wall-editor.mjs`, `portals()`) and in the editor.
- **Players, while the secret door is closed:** they are sent a plain wall.
  - `interaction:'none'`;
  - no `secret`, `locked` or `open` flags;
  - same geometry, sight and movement blocking.
- **Players, when the GM opens it:** they see an open door.
- **Players, when the GM closes it again:** it reverts to a plain wall.

**Fix.**

- Add environment projection to `vttSyncV2ProjectSceneConfigForPlayer` in
  `dnd/vtt/api/v2/_common.php`. Currently it only handles hidden levels.
- Add the same projection to event projection (`vttSyncV2ProjectEventForUser` /
  `vttSyncV2ProjectBoardEventForUser`) for `environment.changed` and the new portal
  and patch events.
  - A toggle of a secret door must reach players as "wall becomes open door" or
    "open door becomes wall".
  - It must not reach players as a raw door event that reveals the secret flag.
  - Use the existing per-audience publishing (`SyncV2PusherTransport::publishAudiences`).
- The server's own movement and sight checks (`WallMovement`) keep using the full
  document. Behaviour stays identical, because a closed secret door blocks like a
  wall.
- Tests:
  - the player snapshot and events never contain `secret`;
  - the GM still sees it;
  - open and close transitions project correctly.

## 2. Vision

### 2.1 "Always visible" must follow PC ownership, not the team field (MEDIUM)

**Problem.** `isAlwaysVisibleAlly` in `dnd/vtt/assets/js/ui/vision-ownership.js` is
true for `team==='ally'`, `combatTeam==='ally'` or non-empty `visionOwners`.
`normalizeCombatTeam` (`state/normalize/placements.js`) defaults any missing team to
`'enemy'`. So a PC token without a team vanishes in the dark, and any ally-team NPC
is always shown.

**Required behaviour.**

- Always visible to players (even in darkness):
  - every PC token (a token linked to a player / primary PC);
  - every token with `visionOwners`, meaning pets, companions and the like that the
    GM gave to a player in token settings (`data-token-vision-owners`, already
    implemented).
- Ally-team NPCs that nobody owns are **not** automatically visible.
- GM-hidden tokens stay hidden.

**Fix.**

- Base the check on the same PC-link resolution the rest of the VTT uses:
  `primaryPc`, a linked player profile, or `pcTokenAssociations` via
  `resolvePcTokenForUser`. Mirror what the server treats as a linked player token
  (`linkedPlayerProfileForPlacement`).
- Keep `visionOwners` in the check.
- Remove the `team` / `combatTeam` checks.
- Update `ui/__tests__/vision-ownership.test.mjs`.

## 3. Floors

### 3.1 A floor without its own polygon plate makes everyone fall (MEDIUM)

**Problem.** Imported maps (Elfsong, Observatory) define upper floors as polygon
"floor plates" (`environment.walls.roofs` entries with `kind:'floor'` and a
`levelId`). `FloorSupport::supported()` (`dnd/vtt/lib/FloorSupport.php`) and
`floorSupported()` (`dnd/vtt/assets/js/ui/floor-support.js`) return `null` (use the
legacy rectangle rule) only when the map has *no* floor plates at all. If any level
has plates, a level without its own plate returns `false`, meaning unsupported
everywhere. For example: the GM adds a new level to an imported map with the normal
Levels editor, and every token placed on it falls through at once.

**Fix.**

- In both files, filter the plates to the token's `levelId` first.
- If that level has none, return `null` so the rectangle-cutout rule applies.
- Add parity tests on both sides.

### 3.2 Deleting a floor leaves stale roof and ramp references (MEDIUM)

**Problem.** The `level.delete` / `levels.set` handling in `SyncV2Store.php` cleans
up the older domains, but not `environment.walls`:

- roofs and floor plates with `levelId` set to the deleted level;
- ramps whose `fromLevel` / `toLevel` point at it.

This leaves stale geometry, and scene-copy reference validation (`ScenePackage.php`)
can later reject the scene. See item 1 of `docs/vtt-edge-case-audit-2026-09-26.md`.

**Fix.**

- In the same transaction as the level removal:
  - remove surfaces whose `levelId` is the deleted level;
  - remove ramps referencing it;
  - bump the walls revision;
  - include the change in the emitted events.
- Verify scene copy and checkpoint restore afterwards.
- Changing a floor's elevation does not re-base absolute wall, roof or ramp heights.
  Leave that as is, and note it in the docs.

## 4. Forced movement (push, pull, slide)

There are two push code paths, and **both** must follow these rules:

- **Ctrl-drag.** Client preview in `ui/forced-drag.js` (`resolveForcedDrag`); the
  server recomputes in `lib/ForcedMovement.php` (`resolve`, `plan`, `assertClear`)
  plus `lib/WallMovement.php`. Both use `forcedDestination`.
- **Ability-driven pushes from JSON-loaded abilities.** `board-interactions.js`:
  `startAutomationMoveSelection`, `handleAutomationMovePointerDown`,
  `getAutomationCollisionStopCell`, `applyAutomationCollisionDamage`. These go
  through `updatePlacementById` with `movementKind:'forced'`.

Route the ability path through the same server-authoritative resolver (send
`forcedDestination`, record through `CollisionEffects`) so the rules and damage
recovery are identical.

### 4.1 Pushed creatures must end in whole squares (MEDIUM)

**Problem.** On a wall or terrain slam, the stopping point is found by bisection
(`resolve`/`resolveForcedDrag`, 32 halvings). This leaves fractional positions such
as column 3.49: tokens off the grid and half inside a square.

**Required behaviour.**

- Let `s` be the travel distance, in squares along the push, at which the creature
  first contacts the obstacle.
- If the creature got **at least 75%** of the way into the square it was entering
  (`frac(s) >= 0.75`), it stays in that square. Slight clipping is acceptable.
- Otherwise it ends in the previous whole square, `floor(s)`. That square is always
  free, because the creature just passed through it.
- Damage counts remaining squares from the final square:
  - obstacle (wall, door, terrain face): **2 + 1 per remaining square**;
  - creature: **1 per remaining square**.
- Client preview and server must produce identical results. The server already
  rejects a mismatch with "Collision changed".
- Tests:
  - contact at 2.8 → stays in square 3;
  - contact at 2.5 → ends at 2;
  - diagonal pushes;
  - a large creature.

### 4.2 Collisions with several creatures at once

**Required behaviour** (confirmed by the user). A pushed creature stops at the
**first** contact; it does not plough through a line of creatures. If it contacts
two or more creatures **at the same moment**, every creature contacted takes 1
damage per remaining square, and the pushed creature takes that damage **once**.

**Status.** `ForcedMovement::resolve` already keeps all ids at the earliest contact
time, and `CollisionEffects::record` inserts the mover once plus each collided id.
The ability-driven path (`handleAutomationMovePointerDown`) only handles the single
creature the user clicked (`clickedPlacement`). Fix it via the unified resolver
above. Test simultaneous contact with two small creatures on both paths.

### 4.3 Slope slam detection: whole-square window plus vertical faces (MEDIUM)

**Problem.** `WallMovement.php` (forced, non-airborne branch) and
`forcedTerrainBlocked` in `ui/forced-flight-terrain.js` measure grade over
1/8-square steps (`run = distance/steps`, slam when `rise/run >= 2`). A tiny bump or
noise inside one square can register as a wall.

**Required behaviour.** Evaluate as the creature moves, sampling every 1/8 square
along the path. Only rising terrain the creature is actually standing on counts;
keep the existing `onTerrain` check, so bridges and floors are excluded.

- **Steep slope.** At sample point `p`, look one full square ahead along the push
  direction. If `ground(p + 1 square) − ground(p) >= 2`, it slams. The window
  slides, so a cliff starting halfway through a square is still caught as soon as
  the window reaches it.
- **Near-vertical face.** A rise of **at least 1 square** within a short horizontal
  distance (at most 1/4 square, a grade of about 4:1 or steeper) also slams, even
  when the total rise over a whole square is under 2. A 1-square-tall box or ledge
  stops the creature.
- **Ignored:** rises under 1 square within a short span, meaning small bumps and
  noise.
- **Contact point:** the start of the rising face (where the rise begins). Snap with
  4.1. A cliff face near the far edge of a square therefore lets the creature stand
  in that square next to the cliff. It only counts as a wall if the push would carry
  the creature through the face.
- **Downhill never slams.**
- Keep server and client identical. Keep the exported `FORCED_TERRAIN_SLAM_GRADE`
  (2) and add a vertical-face constant.
- Tests:
  - 0.3-square bump ignored;
  - 1-square vertical step slams;
  - 1.5 rise over a whole square rides up;
  - 2:1 slope slams;
  - cliff starting mid-square caught;
  - cliff at 7/8 of a square lets the creature stand in that square.

### 4.4 Fliers pushed into rising ground ride up like walkers (MEDIUM)

**Problem.** A flier slams into any ground higher than its altitude, however gentle.
See `WallMovement.php` airborne branch ("Forced flight blocked by rising terrain")
and `forcedFlightTerrainBlocked`. Also `FlightHeight::resolve` returns the height
unchanged for `forced`.

**Required behaviour.**

- When the ground under a pushed flier rises to its altitude, use the same rules as
  walkers (4.3):
  - gentle rises lift `flightHeight` to follow the ground;
  - steep slopes and vertical faces slam.
- A push still never grants voluntary altitude above the ground it rides over.

**Fix.** Apply the 4.3 detection relative to the flier's altitude. In
`FlightHeight::resolve` for `forced`, raise z to the maximum ground height along the
travelled path, up to the slam point.

### 4.5 Pushed over an edge: finish the push, then fall

**Required behaviour** (rules, "Forced Into a Fall"). A creature that can't fly and
is pushed across open space keeps moving the full distance, then falls if it is
unsupported where the push ends. Holes and drops along the way do not stop the push.
Then apply section 5.

**Status.** The server fall check (`FloorGeometry::move` → `fallingDestination`)
already uses only the end position for floors. Terrain drops (off a cliff) produce
no fall at all today. Section 5 covers that.

## 5. Falling (new feature)

### Rules (confirmed by the user)

- Effective fall = squares fallen − the creature's **Agility** score (minimum 0).
- Damage happens only if the **effective** fall is **2 or more squares**. It is
  **2 damage per effective square**, maximum 50.
  - Example: a 3-square fall with Agility 2 leaves 1 effective square, so no damage.
- The creature **lands prone**.
- **Forced downward into the ground:** falling damage for the distance moved, with
  Agility treated as 0.
- **Landing on another creature:**
  - that creature takes the same damage;
  - the faller lands prone in the nearest unoccupied space;
  - the creature landed on is knocked prone if the faller's size is greater than its
    Might score.
- Liquid is ignored. Falling far is out of scope.
- Flying and hovering creatures don't fall. A flier whose flight is interrupted
  (`FloorGeometry::flightInterrupted`: prone, grabbed, restrained, unconscious)
  falls from its `flightHeight` to the ground below.

### When a fall happens

Any movement (walk, shift, forced, teleport) that leaves a non-flying creature
unsupported:

1. **Floor fall:** the server returns `cause:'fall'` from `FloorGeometry::move`.
   Fall squares = elevation of the surface left − elevation of the landing surface.
   Use `FloorGeometry::elevations` plus floor-plate heights.
2. **Terrain drop:** the path crosses a *downward* face that meets the same
   steepness rules as 4.3 mirrored (a drop of 2 or more over a whole square, or a
   near-vertical drop of 1 or more). Fall squares = height at the top edge − landing
   ground height. Walking down a gentle slope is not a fall.
3. **Interrupted flight:** fall from `flightHeight` to the ground.

### Authority and durability

- The server computes the fall distance and returns it in the movement event.
  `movementTransition` already carries the cause.
- In the same transaction as the move, record a pending outcome in the existing
  `CollisionEffects` ledger (add a kind such as `fall`, keeping it idempotent), so a
  reload or crash shows it in the GM's Zone entry recovery panel. Never replay
  damage.
- Agility, Might and size: extend `getAutomationTraitsForPlacement` in
  `board-interactions.js`, which already reads stability and size for heroes and
  monsters.

### UI

1. The token completes its move or push, plays a fall animation, and lands.
2. A small popup appears **right next to the token**. It shows, for example: "Fell 5
   squares − Agility 2 = 3 → 6 damage + Prone". It also lists any creature landed
   on, with its damage and prone state.
   - The damage number is **editable**. There is no stat yet for abilities that
     reduce or ignore falls, so the user adjusts by hand.
   - **Flag this for later:** a character-sheet stat or feature that modifies falls.
3. Buttons are **Apply** and **Dismiss**.
   - **Apply** applies the damage through the existing awaited damage path
     (`applyDamageHealToPlacement` + `awaitSuccessfulPlacementSave`, as in
     `applyAutomationCollisionDamage`), adds the **Prone** condition, and resolves
     the ledger entry.
   - **Dismiss** resolves it without damage.
4. **Only the user who made the move sees the popup.** That is:
   - the player who walked their own token off a balcony;
   - or the user who ran the ability or Ctrl-drag that pushed the creature, even
     when the pushed creature is another player's PC.
5. Tests:
   - the damage formula edge cases (3 − 2 → 0; 4 − 2 → 4 damage; the 50 cap;
     forced-downward with Agility 0);
   - landing on a creature;
   - popup routing to the mover only;
   - recovery after reload before Apply.

## 6. Flight

### 6.1 Flight height must never be below the ground

**Problem.** Token settings send `flightHeight` through `window.submitFlightHeight`
as a `placement.update`. On the server this goes through
`FlightHeight::resolve(..., 'forced')`, which returns the value as-is, so a flier
can be put inside a hill. The old client clamp in `flight-height.mjs` `set()` is
bypassed.

**Fix.** On the server, clamp any set or resolved `flightHeight` to at least
`FlightHeight::ground()` at the token's position, raising it to ground level.
Mirror this in the client. Test it.

## 7. Test coverage gap: the sandbox tests different files from the ones that ship

**Problem.** There are two copies of about 15 terrain and vision modules:

- the prototype copies in `.playwright-mcp/terrain-prototype/`, which include
  built-in test maps;
- the packaged copies in `dnd/vtt/assets/js/ui/`, which are what the real site loads
  via `templates/layout.php`.

`update-sandbox.py` copies the *prototype* versions over the packaged ones inside the
sandbox runtime. So every browser QA pass exercised files that will not ship. The
differences are mostly test-map imports, but they are real code differences.

**Fix.**

- Make `dnd/vtt/assets/js/ui` the single source.
- Have the sandbox install those files, and load test-map registries (Rennet,
  stairs, prison and so on) from a separate sandbox-only module that is not shipped.
- Re-run the browser QA passes from `docs/vtt-reliability-pass-2026-09-26.md`
  against the packaged files.
