# Remove legacy Skyward numbers

This removes the external Skyward number, never the internal `users.id` / `user_id` keys that connect accounts, grades and progress. The new enrollment command rejects Skyward input; roster parsing checks the private source for duplicate IDs but discards them before returning students. The old reset importer no longer writes them. Never run that reset to remove IDs or enroll a new student.

The existing nullable column remains for compatibility. New SQL backups replace its values with NULL, even before the live purge. The Excel export has no Skyward column. Login and reports use other fields; neither requires these numbers. Raw Skyward values must not appear in diagnostic output, plan output, test evidence or committed files.

## Prepared live procedure; requires verified hosting access and action-time approval

1. Use a targeted upload of reviewed files to the verified existing ASL deployment. The repository cPanel task copies the entire checkout and runs legacy-retirement/calendar scripts; do not invoke that broad task blindly for this privacy change. Do not invoke the old account reset, curriculum seeder or a database restore. Code deployment alone does not remove existing numbers.
2. Verify the ASL database/host and take the read-only, aggregate-only preview: `php asl/scripts/remove_skyward_ids.php`. It reports destination, affected-account count and review digest, never names or Skyward numbers. Confirm that the current schema has no users triggers or automatically changing fields that would introduce side effects.
3. Inventory private SQL backups, daily/block snapshots, hosting/database snapshots/binlogs, server-side uploaded roster sources, old review output and relevant logs by location/count only. Do not copy or download raw numbers to investigate. Obtain exact ownership and retention scope; application code cannot erase hosting-provider snapshots or unknown historical copies.
4. A new sanitized SQL backup can preserve current account/grade recovery without retaining Skyward numbers. It is not a backup of the numbers being purged. Verify it in a separate disposable database. Do not restore an older unsanitized snapshot after cleanup: it would reintroduce IDs.
5. Present the verified database and affected count for confirmation. Explain that clearing the column intentionally loses those external numbers from the website; recovery would require a separately retained, authorized offline roster. Confirm historical-copy redaction/deletion separately after exact paths are known; do not delete grade-history backups wholesale.
6. Only after approval run the preview command with `--apply=REVIEW_SHA256 --confirm=REMOVE-SKYWARD-NUMBERS`. The transaction changes only `users.skyward_student_id` to SQL NULL and verifies zero non-NULL values plus an exact fingerprint match of every other user field. Users triggers and ON UPDATE columns cause a fail-closed refusal pending review. It does not create a raw pre-purge backup. MySQL locking and the intended host still need live verification; local tests use disposable SQLite.
7. Verify internal account IDs, account count, authentication flags, grade/history/progress row counts and existing student login/report behavior. Separately sanitize or remove approved historical copies, preserving their other recovery data. Do not claim every internet copy is gone until hosting backups/logs and access are verified.

Known code protection: SQL-download endpoint requires the authenticated administrator; default backup storage is outside the public checkout/document root. Root Apache rules deny private config/lib/scripts/tests/data/backups paths. These are source-code controls, not proof of actual live Apache configuration or historical exposure. No public display of Skyward numbers was found in the current ASL source. Live exposure remains unverified.
